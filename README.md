## Dataset at a glance

The database contains 11 related tables, including `1,200` patients, `6,057` appointments, and `13,216` observations. The data cut-off is 31 October 2026. All identities, organizations, events, measurements, prescriptions, and contact addresses are synthetic. Contact addresses use `example.invalid`.

## Reproduce the database

From this folder, run:

```bash
python3 generate_database.py --db-path synthetic_diabetes.db --seed 20261007
```

The generator uses only Python's standard library. It replaces the target database with a fresh build using the specified seed, then prints row counts, a missing/duplicate audit, SQLite integrity results, and representative constraint-probe results as JSON. Use a different `--db-path` to retain the packaged database while creating another copy.

To review the notebook, open `SQL_Project_Assessment.ipynb` in Jupyter and run its cells from top to bottom. It regenerates the database in the current folder before running its SQL demonstrations and quality checks. A Python 3 kernel is sufficient.

## Intentionally seeded data-quality issues

These defects are generated by fixed counts rather than chance:

- 36 of 1,200 patients (3.0%) have no contact email.
- 60 of 1,200 patients (5.0%) have no smoking status.
- 36 of 1,200 patients (3.0%) have no ethnicity value.
- 12 duplicate email values occur across 24 patients (2.0% of the cohort); shared contacts are plausible within households.
- 36 additional observation rows duplicate an existing observation's patient, appointment, measure, date, value, and unit, each with a separate observation ID. This is approximately 0.27% of the final observation table.

The observation table intentionally has no uniqueness constraint on that natural event key, allowing source-like repeated measurements to remain visible for audit and cleaning exercises. A generator assertion checks every seeded count on each build.

## Schema and integrity notes

The schema uses primary and foreign keys, composite keys in `clinician_site`, `patient_condition`, `medication_catalog`, and `prescription`, `CHECK` constraints for categories and ranges, nullable fields only where missingness is meaningful, and indexes for common patient/date and clinic/status joins. Observations have a composite foreign key to the appointment and patient pair. SQLite foreign-key enforcement is enabled by the generator and checked before packaging.

The final database passed `PRAGMA integrity_check` (`ok`) and `PRAGMA foreign_key_check` (zero rows). Six representative invalid inserts were rejected: category `CHECK`, `UNIQUE`, `NOT NULL`, foreign key, composite primary key, and measurement range/type rules.

## Privacy, ethics, and use

No real patient data, external source records, real clinics, or reachable contact details were used. Patient identifiers are generated; emails use the reserved `.invalid` domain. Names are randomly selected from small code-defined lists and may repeat. The cohort and measurements are fictional approximations made for database education. They are not representative, clinically validated, or suitable for healthcare decisions or inference about real groups. The intentionally duplicated data and missing fields are plainly disclosed for assessment and data-cleaning practice.
